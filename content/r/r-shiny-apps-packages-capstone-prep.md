### Key Concepts

- Shiny apps have two parts: ui defines the HTML layout and inputs; server is a function(input, output, session) that produces outputs reactively; reactive expressions cache and re-execute only when their inputs change.
- reactive({...}) returns a cached value recomputed when inputs change; observe({...}) runs for side effects (no return value); eventReactive(trigger, {...}) and observeEvent(trigger, {...}) wait for a trigger.
- req(input$x) short-circuits a reactive if input$x is NULL/empty/falsy, preventing errors before the user has filled in the form; use it liberally in render* functions.
- An R package needs DESCRIPTION (metadata + dependencies), NAMESPACE (what to export and import), R/ (functions), man/ (docs generated by roxygen2); usethis automates scaffolding and renv pins dependencies.
- R CMD check is the gatekeeper: 0 errors, 0 warnings, 0 notes is the goal; testthat for unit tests; pkgdown builds a documentation website; GitHub Actions runs check on every push.

```r
library(shiny)
ui <- fluidPage(
  titlePanel("MPG Explorer"),
  sidebarLayout(
    sidebarPanel(
      selectInput("cyl", "Cylinders:", choices = c(4, 6, 8), selected = 4),
      sliderInput("bins", "Bins:", min = 5, max = 50, value = 20)
    ),
    mainPanel(
      plotOutput("hist"),
      verbatimTextOutput("summary")
    )
  )
)
server <- function(input, output, session) {
  filtered <- reactive(mtcars %>% dplyr::filter(cyl == input$cyl))
  output$hist <- renderPlot({
    req(filtered())
    hist(filtered()$mpg, breaks = input$bins, col = "steelblue",
         main = paste("MPG distribution for", input$cyl, "cylinders"))
  })
  output$summary <- renderPrint({ req(filtered()); summary(filtered()$mpg) })
}
shinyApp(ui, server)
```

### Common Pitfalls

- Forgetting req() in render functions — the first render fires before the user has provided inputs, so input$file is NULL and read.csv(NULL$datapath) throws; wrap dependencies in req() to short-circuit cleanly.
- Using observe() when you mean reactive() — observe() runs for side effects and returns nothing; reactive() returns a cached value; using the wrong one causes silently missing outputs or excessive re-execution.
- Circular reactivity — a reactive that updates the input it depends on creates an infinite loop; use isolate() to read an input without subscribing to it, or update inputs only inside observeEvent() with care.
- Exporting internal functions in NAMESPACE — only export functions users should call (with @export); internal helpers stay un-exported; over-exporting bloats the API and prevents safe refactoring.
- Skipping R CMD check before CRAN submission — CRAN enforces 0 errors/warnings/notes; run devtools::check() locally and on GitHub Actions (with r-lib/actions) before submitting; minor notes still cause rejection.

### Interview Questions

- 1. What are the two main parts of a Shiny app? — ui (the HTML layout and input controls) and server (a function(input, output, session) that produces outputs reactively); shinyApp(ui, server) ties them together.
- 2. What is the difference between reactive() and observe()? — reactive() returns a cached value recomputed when inputs change (lazy, memoized); observe() runs for side effects immediately (eager, no return value).
- 3. What does req(x) do in a render function? — req(x) short-circuits the reactive if x is NULL/empty/falsy, preventing errors before the user has filled in inputs; it silently stops execution without throwing.
- 4. What files does an R package need at minimum? — DESCRIPTION (metadata + dependencies), NAMESPACE (exports/imports), R/ (functions), man/ (docs auto-generated from roxygen2); usethis automates scaffolding.
- 5. What does R CMD check verify, and what is the goal before CRAN submission? — It checks package structure, examples, tests, and documentation; the goal is 0 errors, 0 warnings, 0 notes; CRAN rejects on any error or warning and most notes.

Use reactive() for the filtered data and req() to guard against empty filters.
Suggested approach:
  - Define ui with sidebarLayout, three inputs in sidebarPanel, three outputs in mainPanel
  - Use a reactive() to compute filtered_data based on the three inputs
  - Wrap the filter chain in req(input$genre, nrow(df) > 0) to short-circuit empty states
  - Use DT::renderDataTable() for the table and renderPlot() for the ggplot scatter
  - Add a downloadButton() with downloadHandler() to export the filtered rows as CSV
