# Flask-Migrate (Alembic) and Database Migrations

## Flask-Migrate (Alembic) and Database Migrations

### Why It Matters

Set up Flask-Migrate (Alembic) to version-control your schema, autogenerate migrations from model changes, edit them by hand when needed, and apply upgrades/downgrades across environments.

### Prerequisites

- Stage 10: SQLAlchemy and Flask-SQLAlchemy
- Conceptual understanding of DB migrations (forward + rollback).

### Topics

- flask db init — the migrations/ folder
- flask db migrate -m 'msg' — autogenerate
- flask db upgrade / downgrade
- flask db stamp — mark a revision as applied without running it
- Editing autogenerated migrations (autogenerate misses some changes)
- Op directives: add_column, drop_column, create_index, alter_column
- Multi-environment migrations (dev SQLite, prod Postgres)
- Branching, merging, and resolving divergent migration histories

### Key Concepts

- Alembic stores revision files (Python) under migrations/versions/; each file has a down_revision pointing at its parent, forming a linked list.
- Autogenerate compares SQLAlchemy metadata to the live DB and writes a candidate migration; ALWAYS review it — it can't detect renames (treats them as drop+add) or data-dependent changes.
- Downgrade must reverse upgrade; if you skip the downgrade function you'll be unable to roll back a bad deploy — write it always, even if it's a no-op for forward-only changes.
- flask db stamp <revision> marks the alembic_version table without running the migration; use it to align an existing DB with your migration history (e.g., after importing a legacy DB).
- Migrations are code — commit them to git, review them in PRs, and run them in CI on a throwaway DB to catch syntax errors before deploy.

```bash
pip install Flask-Migrate

# In create_app, after db.init_app(app):
#   from flask_migrate import Migrate
#   migrate = Migrate(app, db)

flask db init         # creates migrations/ folder
flask db migrate -m "initial"   # generates migrations/versions/<hash>_initial.py
flask db upgrade      # applies to DB
flask db current      # shows current revision
flask db history      # shows revision chain
```

### Common Pitfalls

- Trusting autogenerate to detect column renames — Autogenerate sees a drop + add and you lose data; for renames, hand-edit the migration to use op.alter_column(table, old, new_column_name=new) or rename_table().
- Forgetting to import all models before migrate — Alembic reads SQLAlchemy metadata; if a models.py is never imported, its tables are invisible to autogenerate. Always import models in app/__init__.py inside create_app().
- Running migrations on dev SQLite that won't work on prod Postgres — SQLite doesn't enforce types or support ALTER COLUMN the same way; test migrations on Postgres in CI before deploying. Use op.batch_alter_column for SQLite-compat on dev.
- Skipping the downgrade function — Without downgrade(), flask db downgrade fails and you can't roll back a bad deploy; always write downgrade even if it's a partial reverse.
- Two devs creating migrations off the same parent — You get a branched history; resolve with `flask db merge -m 'merge heads'` to create a merge revision before applying on prod.

### Real-World Applications

- Patreon's Flask services use Flask-Migrate against sharded Postgres; migrations are reviewed in PRs and applied in a rolling deploy with backwards-compatible code first.
- Lyft's admin Flask apps use Alembic with batch_alter_column for SQLite-compat in dev and native ALTER in prod Postgres, gated by CI tests.
- Pinterest's Flask services ran Flask-Migrate + Alembic for years before migrating to a custom expansion-based schema tool that handles multi-shard rollouts.
- Netflix's security tooling uses Alembic migrations checked into git and applied via a deploy-time Kubernetes job (init container) before the new pods serve traffic.

### Interview Questions

- 1. What's the difference between flask db migrate and flask db upgrade? — migrate generates a new revision file by comparing models to the DB; upgrade applies pending revisions to the DB.
- 2. Why must you review autogenerated migrations? — Autogenerate can't detect renames (treats as drop+add), data-dependent changes, or check constraints; review every revision before applying.
- 3. What does flask db stamp do? — It writes the revision id to the alembic_version table without running the migration; used to align an existing DB with your history (e.g., after importing legacy data).
- 4. How do you handle two devs creating migrations off the same parent? — Run `flask db merge -m 'merge heads'` to create a merge revision linking both branches before applying on prod.
- 5. Why is SQLite problematic for testing migrations? — SQLite has limited ALTER TABLE support; some migrations that work on Postgres fail on SQLite. Use op.batch_alter_column for dev compat and run migration tests on Postgres in CI.
